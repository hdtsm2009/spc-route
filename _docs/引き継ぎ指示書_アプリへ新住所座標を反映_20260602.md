## 1. 背景・経緯（今日判明したこと）

1. スポカフェ管理画面DBには **番地付き住所（例: 東京都中野区中野3-34-16）＋建物＋郵便番号が入っている**。
   - これまで使っていた `_マスタデータ/店舗一覧マスタ_20260331.txt`（3行1レコードの旧マスタ）は、**エクスポート時に住所が「都道府県＋市区町村」まで切り詰められ番地が落ちていた**。緯度経度は元々空。
2. そのため旧パイプラインは、番地の無い住所を **Google Places の店名検索（POI）でジオコーディング**して座標を補完していた（ソース名 `スポカフェマスタ補完(POI)`）。
3. **この店名検索ベースの座標に誤マッチが多発**していることが、新データとの突合で判明：
   - 国土地理院ジオコーディングとの距離が **1km以上ズレる店が109件**（例: ID11488「東京・台東区元浅草」の住所なのにGoogle座標は**830km先**＝別店を拾っている）。
   - 中央値のズレは19mなので大半は問題ないが、**テール100件超が完全な誤ピン**。
4. 今日、スポカフェ管理画面から**番地付きの新公式エクスポート**が出てきたので、これを正本に切り替えられる状態になった。

## 6. 重要な注意点・ハマりどころ

1. **JOINキーが違う（最重要）。**
   - `api/stores.json` の `店舗ID` は **内部ハッシュID（例 `S6143B6FE`）**で、電話番号から生成されている。`_data/store_id_map.json` は `電話番号 → 内部S-ID` のマップ。
   - 一方 (a)(b) の `店舗ID/スポカフェ店舗ID` は **スポカフェの数値ID（例 13223）**。
   - 両者は直接一致しない。**JOINするなら電話番号 or 店名＋住所で突合**が必要。(a)には電話番号列がある（(b)生成時には電話番号を持たせていないので、JOIN前提なら(a)から電話番号を引くか、(b)を電話番号付きで作り直す）。
   - → だからこそ §4 の「パイプライン正攻法（ソース差し替え）」の方が、IDの整合を既存の名寄せロジックに任せられて安全。
2. **掲載店数が変わる。** 旧マスタ由来1,537 → 新エクスポートは掲載1,815（ユニークID）。増減があるので、閉店除外ロジック（`l3_verdicts.json` / フェーズ06）との兼ね合いを確認すること。
3. **海外30件**（§3-b）は座標が取れない。国内営業ツールなら除外でOKだが、表示要件は確認。
4. **座標の出所・精度カラムを正しく付ける。** 既存は `geo_quality`(A/B) と `ジオコーディング精度`(詳細/町名…)。新データは「住所ジオコーディング(GSI)」由来と分かるようソース名・精度を更新する（例: ソース `スポカフェ公式(番地)`、精度 `詳細(住所GSI)`）。後から「どの座標が信頼できるか」を追えるようにする。
5. **国土地理院APIは無料・キー不要**だが、連続アクセスは `SLEEP` で間隔を空ける（`座標統合データ生成.py` は0.12秒）。
6. **住所はDB側が正。** Google補完住所（旧 `_納品_スポカフェ掲載店住所還元_20260530/`）は店名検索由来で誤マッチありなので、**住所・座標の正本には使わない**。参考/救済のみ。
